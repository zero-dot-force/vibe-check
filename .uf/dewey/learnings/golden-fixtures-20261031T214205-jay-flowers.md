A second golden-regeneration switch in a Go test package fails asymmetrically in the contributor's direction of travel: the documented switch (`go test ./pkg/ -update`) regenerates the established golden families while the new family's comparison test fails instead of regenerating, so the divergence surfaces as a red test whose message must teach the undocumented second incantation. When folding a new golden family into an existing package's `-update` flag: reference the already-declared package-level flag directly (e.g. `*updateGoldens` from cmd/vibe-check/report_test.go — both test files compile into the same test binary), never re-declare `flag.Bool("update", ...)` in a second file (duplicate registration panics), keep the write-then-return single-writer shape so comparison and write never race, and update the flag's usage string plus any doc comment that enumerates the golden families it governs. In vibe-check, `-update` is the regeneration convention in both golden-bearing packages (cmd/vibe-check, cmd/coverage-ratchet); PR #75's WRITE_GOLDEN=1 in TestRunAnalyze_GoPathByteRegression was a one-off — no other new test used it, and internal/ripwireadapter's recorded goldens are hand-computed read-only pins (testdata/recorded/golden-notes.md) regenerated by a manual re-record procedure, not a test switch.
